## 1. 背景

「資料作成・変換表」ページの【京阪 あて紙】について、クライアント関西ぱどから修正指摘を受領。
指摘内容を現行実装・実データ・現行マクロと突き合わせた結果、**指摘12項目のうち6項目は既に満たしており、
実際に手を入れるのは6項目**であることを確認した。

### 入力データの列対応（実データで確定）

`Downloads\京阪北版CSV リーダー名あり.xlsm`（北版1248号・1738行）および
`Downloads\アドバリュー用.xlsm` の `1_地区マスタ` シート（南版1211号・504行）で確認。**両者の列構成は完全に同一**。

| 列 | ヘッダー | 用途 |

| A | 配布日 | ファイル名 |

> 北版353/353・南版174/174で完全一致（10101→`010101`→「01 ぱど」／911001→「91 ぱど」）。
> ＝ 担当地区コードは本来6桁で、Excelが先頭0を落としているだけと判断できる。

## 2. 対応方針（オーナー確定・2026-07-23）

| 論点 | 決定 |
|---|---|
| 担当地区の印字 | **6桁ゼロ埋めで統一**（北版 `010101` ／ 南版 `911001`）。テンプレ固定セル `C4=0` は使わない |
| 南版に追加の0 | **付けない**（元々6桁のため。配送物名「91 ぱど」と整合） |
| 1枚だけ再出力 | **その地区だけの xlsx をダウンロード**。カンマ区切りで複数コードも可 |
| 南版の検証 | **手元の1211号データで作成 → オーナーが目視確認**（南版はマクロの正解あて紙が無い） |
| 上部の部数 | **ぱど行の部数**（明細は各行のL列）＝現行マクロと同じ意味。実装だけ「1行目」→「ぱど行」に正す |
| 中央揃え | **左右＋上下の両方**（用紙に対する中央。セル内文字揃えではない） |
| Q列サイズ | **対応不要**（既に部数の直前に入っている） |

### 🔴 設計書の記述の訂正
**「ゴールデン突合を緩めていない」という §5 の記述は誤りだった。**
D4 の期待値に実装と同じ `A.area_code6` を通していたため自己参照になっており、
ゼロ埋めが壊れても両辺が同じように壊れて検出できなかった。
→ 期待値を `str(macro値).strip().zfill(6)` とテスト内で組み立てる形に修正。
**変異テストで検証済み**：`area_code6` からゼロ埋めを外すとゴールデンが353地区で落ち、戻すと通る。

### テストの補強（"見せかけの緑"の解消）
- 未知コード通知テストの `or "見つかり" in msg` は常に真だった → `"099999" in msg` に厳密化
- overflow警告テストの `"13"` は画面のベタ書きを見ていた → `A._MAX_DETAIL_ROWS` と連動
- データ0件テストが**他タブの `st.info` を拾って常に通っていた** → 「0件」の文言まで確認
- 南版のUIテストが生成ボタンを押していなかった → 実際に押してダウンロードまで到達を確認
- 明細13行超の切り捨てが出力レベルで無テストだった → 集計行(18行目)を侵食しないことを固定

### 🔴 オーナー指示による訂正（2026-07-23）
初版では南版のエリアを「エリア1／エリア2」と**振り直していた**が、オーナー指示により撤回：

> 「エリア表記等は基本的にCSVをそのまま拾って。エリア１，２とか勝手に変えないでほしい。」

→ **エリアは担当地区コードの値をそのまま使う**（北版 `1`〜`5` ／ 南版 `91`,`92`）。
   これは配送物名の番号（「01 ぱど」「91 ぱど」）と一致する、CSVに実在する値。
- 実データ確認：北版 {1:21,067／2:35,729／3:30,794／4:29,486／5:31,156}（**従来どおり**）
  ／南版 {91:42,573（89地区）／92:32,418（85地区）}
- 💡 **教訓：CSVにある値を、見やすさや一貫性を理由に別の値へ振り直さない。**
  元の値のまま出す。表記を変える必要があるならオーナーに確認してから。
